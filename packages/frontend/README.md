# Frontend Configuration (`@cashingularity/frontend`)

Wallet (`/`, also `/wallet`) is the home workspace, alongside Markets (`/market`), Arcade (`/arcade`), and Settings (`/settings`). The sticky header contains the GitHub source link, notifications, and a profile menu for Settings, wallet switching, and Light, Dark, or System appearance. Send, Receive, Batch Pay, and connected-app details open as wallet popups; unsent inputs survive closing and navigation. The legacy `/batch` URL opens Batch Pay over Wallet. BCH Mainnet is selected on startup and Explore Sandbox in the profile selector or Settings enables Paper Trading. Balance, history, and broadcast requests use `/api/chain/utxos`, `/api/chain/history`, and `/api/chain/broadcast`, with `/api/wallet` compatibility aliases. WizardConnect and compatible injected wallet providers are available for external signing. Real price feeds identify their source and observation time; missing live data is shown as unavailable.



## Wallet profiles and payments

Create or import an English 12- or 24-word BIP39 phrase using the wallet modal. The app uses BIP44 receive and change paths `m/44'/145'/0'/0/0` and `m/44'/145'/0'/1/0` without a BIP39 passphrase. Wallet keys are held in memory while unlocked. By default each profile is saved using AES-GCM with a randomly generated device key in localStorage, and unlocked only after you select it and confirm Unlock & activate. The key is stored alongside the ciphertext, so anyone who can access the browser storage can recover the profile. Optionally register or link a backend security account to protect the profile. AES-GCM encryption derives its key using PBKDF2-SHA256 (310,000 iterations), the password, and an account factor released by the server only after authentication. That factor is never persisted in the browser. Disabling persistence leaves a new unprotected profile session-only. Save a recovery phrase separately. The profile menu switches between saved wallets and Paper Trading. Settings handles recovery phrase reveal, network switching, and session lock. Switching a local wallet’s network keeps the same profile identity and backup. WizardConnect restores an encrypted session when possible, discovers balances from public address data, and enables signing only after live peer authorization. No recovery phrase is sent to XO or other endpoints by this flow.

Send lists BCH and held fungible CashTokens only. Native BCH and Batch Pay exclude token-bearing inputs; a CashToken transfer preserves every selected NFT and sends token change back to the wallet. Token dust limits are calculated from the encoded output. All live transfers show exact outputs and fees, verify signatures locally in CashVM, and broadcast only after confirmation. Zero spendable BCH disables native sending. Fiat batches fetch a fresh quote lock, recalculate all rows, display the original fiat values and resulting satoshis, and refuse to broadcast after expiry. Fiat review checks the spot and FX source timestamps as well as the 60-second quote expiry. An expired or stale quote must be refreshed and reviewed again. Payments rely on the chain service for accurate UTXO and token metadata. Contract previews still use illustrative covenant state and cannot be broadcast until a verified contract transaction is available. Network failures and broadcast errors require checking the displayed transaction ID before retrying.

Transaction receipts saved in this browser contain public transaction data and their originating local profile ID. The compact history merges receive and change-address activity and shows known transaction details. The session bell scopes signing requests, broadcasts, confirmations, and approved dApp connections to the selected profile and network. In Paper Trading it shows resolutions for rounds that profile entered. Contract signing remains blocked: an owner recovery proof alone does not implement prediction settlement and payout rules. The current prototype contract descriptors are not deployment artifacts.

Local contract review can preview a wallet-funded P2SH32 template. Public deployment rejects contract preparation and offers Paper Trading. The lock is exactly the requested stake. Total spend adds the actual miner fee and the BCH reserved in an optional wallet-owned CashTokens receipt. Receipt dust depends on the serialized output. A failed preparation shows the requested stake and available spot price without presenting a synthetic pool transaction.

In Paper Trading, the market ticket offers Stake and Cash Out for the active round. Cash-out uses the displayed outcome’s pool share as a mark on the locked payout for the amount sold. The reviewed amount is credited to the virtual balance on confirmation, and only the remaining stake can settle at expiry. Cash-out quotes are checked against the current pool and expire with the round. Winning settlement distributes the losing pool after fees and reserves, preserving the winning stakes’ principal.

## Wallet quick actions

Send and batch drafts use sessionStorage; named transfer lists use localStorage. Batch Pay starts with four empty rows; every row can be removed, and Clear All leaves zero rows. Raw Text / Bulk Edit and interactive rows share a draft model, including typed, unrecognized currency input and validation errors. CSV, TSV and XLSX files can be dropped or selected (100 recipients, 5 MB file limit); the first worksheet is read without evaluating formulas. Formula cells, external worksheet references and oversized XML are rejected. Named columns Address, Amount, Currency and Label are supported. Paper Trading exposes Set Virtual Balance and never broadcasts practice sends. USD, EUR, KZT, RUB, GBP, USDT and PUSD are units of account; every output is native BCH. USDT and PUSD use the quote's USD reference conversion, not token transfers or a Tron payout.

## Password and Authenticator security

Settings contains network switching, seed backup, session lock, scoped wallet removal, and Password & Authenticator enrollment. The Create New Protection / Sign In to Existing Account toggle leads from password verification to a dedicated Authenticator popup; new protection opens QR enrollment automatically. `/api/auth/register` returns an account and transient encryption factor. Login starts with account name and password (`begin: true`): accounts with TOTP return a short-lived, IP-bound challenge without an encryption factor or new session. A second login request with the challenge token and code completes authentication. Challenges expire after two minutes, permit at most five code attempts, and can succeed only once. `/api/auth/totp/setup` generates a real Base32 secret and otpauth URI; `/api/auth/totp/verify` enables RFC 6238 SHA-1, 30-second, six-digit codes. Scan the QR with Google Authenticator or Authy. After enabling, password plus an unused code is required to unlock a protected profile. Successful unlock keeps only that profile authorized for signing in memory until Lock or reload, without retaining the password, TOTP code or server encryption factor. Seed reveal still requires fresh, single-use authorization. Used codes cannot be replayed. Lock and removal revoke that profile’s authorization; logout clears all in-memory wallet keys and permits. Stake review never requires creating a security account: active wallets and Paper Trading proceed directly; disconnected users are asked to select/connect a wallet.

Backend records contain scrypt password hashes and encrypted TOTP/account material, encrypted using AES-256-GCM under `.cashingularity-data/account-security.key`. The key file must remain private and be backed up with the database. Account data is excluded from analytics exports. Authentication sessions use short-lived HttpOnly SameSite cookies, request throttling and no-store responses. Use HTTPS outside localhost. Wallet seeds and private keys stay in the browser; the backend never receives them. Recovery phrases remain the independent wallet recovery mechanism.

## Connected Applications

The list starts empty. Legacy demo records are discarded. Only active cross-origin browser handshakes plus explicit address-access approval appear as connections. HTTPS applications (or a different localhost port) must implement this protocol:

1. Open a compatible app URL in the pairing form. Its iframe receives `CASHINGULARITY_WALLET_HELLO` with version 1, requestId and a random challenge.
2. Reply to the exact wallet origin using `postMessage` with `CASHINGULARITY_CONNECT`, the same version/requestId/challenge, and a transferred MessagePort. The wallet checks the source window and origin.
3. After approval, the port receives `CASHINGULARITY_CONNECTED` with accounts and the sole permission `bch_getAddresses`. RPC requests `{id, method:'bch_getAddresses'}` return the approved address. No signing or token approval permission is granted.
4. Respond to `CASHINGULARITY_PING` with `CASHINGULARITY_PONG`. Disconnect, iframe reload, wallet/network change, or missing heartbeats revoke the session. Connections are not fabricated or restored from storage.

A `wc:` URI alone is not a connection; this manager uses the browser handshake above, rather than claiming WalletConnect relay compatibility. External wallet signing remains available separately through WizardConnect or an injected wallet provider.

## Market epochs

The 1m, 5m, 1h and 24h controls select actual backend market series and step by 60, 300, 3600 and 86400 seconds. Custom changes the chart range while keeping the market series at 5m. The scoreboard displays the live round and up to eight recent reported closes. UP, DOWN and FLAT describe the close relative to the strike in cents. The winning outcome is shown separately. Resolution History loads older results on demand and reports the oldest and newest available closes.

Connected Apps opens through Connect dApp / Paste Pairing Code. HTTPS browser URLs and `cashingularity://connect?url=...` links use the verified browser handshake described above. The approval popup displays the app origin, address, network and permissions, with Approve and Reject actions. `wc:` relay codes and external-wallet `wiz://` codes are explained explicitly and never recorded as successful dApp sessions.

## Cloudflare Turnstile

Every registration and login request, including the second TOTP challenge step, requires `cfTurnstileToken`. The isolated verification origin loads the official explicit-render Turnstile script, clears expired tokens and re-renders after each auth attempt; provider JavaScript never executes in the wallet document. The backend posts tokens to Cloudflare Siteverify before hashing passwords or completing a TOTP login. IP/account throttles remain in place; real keys also enforce the action, allowed hostname and a local single-use token guard. Provider outages fail closed.

Set `TURNSTILE_SECRET_KEY` on the backend and `VITE_TURNSTILE_SITE_KEY` before building the frontend for deployment. The public site key is not a secret. Set `TURNSTILE_ALLOWED_HOSTNAMES` to the separate verification hostname (comma-separated if several are deployed), matching the hostname returned by Siteverify. Production requires real keys. Localhost/test defaults use Cloudflare's official dummy keys, which provide integration testing rather than real bot resistance:

- Site key: `1x00000000000000000000AA`
- Secret: `1x0000000000000000000000000000000AA`

Documentation: https://developers.cloudflare.com/turnstile/troubleshooting/testing/ and https://developers.cloudflare.com/turnstile/get-started/server-side-validation/.

The header retains one practice-mode toggle and the profile selector. The summary card displays the active profile name and an unconnected Connect Wallet action. Password unlocks select one saved profile ID; labels and addresses remain inside encrypted storage. Device-key backups can be unlocked without a password after explicit selection. The wallet modal closes with Escape, and browser dApp handshakes time out after ten seconds without granting access.

## Active wallet selection and batch review

The active live profile ID is saved as `cashingularity.activeLiveProfileId.v1`. Live mode restores the preferred unlocked profile (or another available live profile); Paper Trading retains that live selection for the return trip. Password-protected profiles still require explicitly selecting and unlocking the saved profile. Reloading can restore device-key wallets without activating the practice account by mistake.

Batch Pay shows one popup title, an accessible styled file picker and a File Format Guide with column definitions and two example rows. Review remains clickable for empty or invalid drafts and reports a specific inline error for empty recipients, invalid/unconfirmed rows or a missing on-chain wallet. Unknown or ambiguous typed currencies cannot produce payable rows. `scripts/profile-batch-ux-smoke.cjs` verifies these flows and selection persistence at 1440px and 390px.

## Appearance and market ticket layout

The profile menu offers Light, Dark, and System appearance, saved as `cashingularity.theme.v1`. Both charts, forms and popups follow it. On market details, the order ticket defaults to a sticky right column above 1000px. Its More options menu offers right, left and full-width placement and houses the Contract Engine selector. ## Market overview and epoch prices

Canonical market links and timeframe switches select the current open epoch. Time-indexed links and history selections open a result in the scoreboard, with the live charts and ticket still on the current open epoch. Open stake reviews are invalidated when a round expires or the wallet changes. The spot/target chart loads real candle opens and observed closes through `/api/markets/candles?interval=...&limit=...&endTimeMs=...`, then merges timestamped ticks. Historical window requests are read-only and cannot update the backend spot or FX quote. Missing exchange observations remain unavailable.

The Symbol Overview is rendered locally with bundled lightweight-charts using backend candles and live spot prices; no TradingView scripts, embeds or automatic network requests are loaded. Range buttons show 1D, 1M, 3M, 1Y, 5Y and All. The backend currently caps a request at 200 candles: long ranges explicitly show the available date coverage instead of fabricating older prices. The 24-hour change uses a completed historical minute candle. A passive TradingView library credit link remains. The separate epoch chart and settlement use backend observations independently.

The wallet document CSP allows only same-origin scripts and bundled crypto WebAssembly. Turnstile runs on a **different verification-only origin**, in an iframe sandbox that permits scripts and that distinct origin, but no top navigation or popups. The verification service serves only three static challenge files; no wallet pages or APIs. Parent/child messages check exact origins, window identity and a random nonce, and exchange only public challenge configuration and a short-lived bot token. Authentication still verifies tokens server-side. `npm start` starts this service on loopback port 3001 alongside the wallet on 3000. For deployment, proxy a dedicated HTTPS verification origin to this service, set `VITE_TURNSTILE_FRAME_ORIGIN` to that different hostname at frontend build time, and set `TURNSTILE_WALLET_ORIGINS` to the exact wallet origin(s) on the backend. Same-hostname frame configuration is rejected. The local wallet at localhost uses 127.0.0.1:3001 so wallet cookies are not shared with the verification host. Configure the real Turnstile keys/domain for the verification origin. Authentication fails closed if isolated verification is unavailable; local development uses Cloudflare’s official test keys.

## Connected wallets, stake controls and chart smoothing

The wallet modal separates Connected, Connect, Create and Import. Connected groups unlocked local wallets, external/watch-only sessions and encrypted saved profiles. Lock clears one saved local key from memory. Remove deletes only the selected browser profile. After reload, select a saved profile and explicitly unlock it. External disconnect clears the signing session and retains its address as watch-only. The Connect form remains available for a new pairing.

Enable signing on a Watch-only profile by entering the BIP39 phrase that derives the watched P2PKH address on its selected network. Standard and token-aware forms are recognized. The profile retains its ID, name, address and history. By default the key stays in memory and Lock returns the profile to Watch-only. A saved Watch-only backup can be opened explicitly after reload. Opting in to an encrypted signing backup replaces only that profile's Watch-only backup and preserves its existing password or account protection.

Stake input accepts exact BCH values down to satoshis, with a 546-satoshi minimum and no silent decimal rounding. MAX excludes CashTokens inputs and reserves an estimated network fee. Four presets are stored in `cashingularity.stakePresets.v1`; clicking sets the amount, and Shift-click adds it. The Developer Contract Inspector is collapsed inside the position menu.

The orange reference chart uses monotone cubic display interpolation and curved rendering, with one-second detail near the live edge. A minimum two-minute context window seeds newly opened epochs. Long histories use a bounded display series. Interpolated points and carried-forward last prices never enter position settlement, expiry closes or transaction construction. Header prices and settlement continue to use raw, timestamped exchange observations.
